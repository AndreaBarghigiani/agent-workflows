# Deliver an issue

This skill coordinates exactly one GitHub issue. When the requested target resolves to a GitHub milestone rather than an issue, stop and suggest [`deliver-milestone`](../deliver-milestone/SKILL.md) as the actionable entry point; never silently redirect into it. `deliver-milestone` applies the converse guard for issue targets.

Read the consumer project's root `AGENTS.md`, context and engineering workflow, the originating issue, its parent/blockers, and relevant architecture decisions. Before planning, use the configured Basic Memory project to retrieve relevant project context, decisions, and patterns; pass applicable findings to implementation and review. If memory access or project routing is unavailable, disclose that gap and continue with repository and issue evidence. If scope is unclear, use [shape-issue](../shape-issue/SKILL.md). GitHub holds durable scope and status; do not create another tracker.

Resolve applicable service and access guidance before planning from the consumer's instructions and documentation; when it keeps an integration index or reference, read only the matching entry and pass its target context, preferred access method, and known limits to implementation and review. For this library's GitHub issue workflow, configured `gh` is a prerequisite: verify relevant read access when needed with an explicit repository and a targeted safe read. A signed-out browser alone is not a blocker. Do not install tools or change authentication implicitly; report exact access gaps.

Discover applicable lint, formatting, and other required checks from the consumer's root and path-specific `AGENTS.md`, project documentation, and tooling configuration. Resolve exact commands, execution context, and required scope before delegation; distinguish formatting writes for implementation from read-only validation for review. Follow [consumer check guidance](../../../docs/consumer-checks.md); resolve consequential conflicts or missing commands without imposing tools or narrowing mandatory checks.

Map acceptance criteria to bounded implementation slices and verification. Continue from a plan already accepted in this session. Otherwise present the concrete plan together with the resolved implementer and reviewer (provider, model, and reasoning effort for each role) and wait for acceptance before delegating or otherwise starting implementation, unless the project's `AGENTS.md` explicitly waives plan acceptance or acceptance is explicitly inherited from an accepted `deliver-milestone` execution plan. Inherited acceptance satisfies this checkpoint only within that plan's stated boundary; a material departure escalates to the milestone caller rather than proceeding silently or seeking fresh per-issue approval. A model named in the user's request overrides the profile for that role and is reported at this checkpoint, but it does not count as plan acceptance. Resolve material scope or product changes before dependent implementation.

Use the `issue-implementer` profile with [implement-issue](../implement-issue/SKILL.md) when the client supports custom agents and delegation is permitted. Resolve each role from the consumer's `.agents/delivery-profiles.json` when present, following [delivery profiles](../../../docs/delivery-profiles.md) for overrides, selection, fallbacks, and availability checks. A direct invocation stays coordinated by the calling session: the optional `orchestrator` role configures only the per-issue coordinators `deliver-milestone` launches and introduces no automatic delegation here. Launch each child inheriting the parent session's permission mode by default: omit `runtimeMode`, or pass `"inherit"` where the launch contract supports it. Choose a narrower mode only when the owner explicitly requests supervised execution; a review-only brief does not justify narrowing. Pass the issue, accepted scope, non-goals, relevant paths, applicable technical skills, dependencies, and exact formatting and verification commands with execution context and required scope. The worker should not have to infer the coordinator's product decisions.

Keep ambiguous architecture and scope decisions with the coordinator. If the worker cannot complete a bounded slice without a new decision, resolve it before another pass. Do not impose the shared repository's layout or commands on the consumer.

After implementation, use an independent `issue-reviewer` with [review-issue](../review-issue/SKILL.md), passing the issue, actual diff, relevant project rules, retrieved Basic Memory context, exact required read-only validation commands with execution context and scope, the revision to review, and implementation check evidence. The reviewer must execute applicable validation independently. Resolve actionable findings with bounded implementation passes. Once review verifies the required outcome, the reviewer returns a draft verified summary with its evidence. The coordinator checks that evidence against the acceptance criteria and mandatory checks, then posts the single verified comment on the GitHub issue; the reviewer never posts it. Use this comment as source material when drafting the pull request description. Capture only reusable decisions or patterns in Basic Memory, using the applicable schemas; the issue comment remains the record of this issue's implementation. If independent agents or requested models are unavailable, say so and ask the owner how to proceed; complete a clearly disclosed single-agent workflow or substitute another model only with the owner's accepted answer, and never claim independence or a model split that did not occur.

Verify the resulting diff and ensure the consumer's required checks pass on the relevant revision. Reuse valid implementation and independent review evidence when the relevant revision, scope, and verification inputs are unchanged; do not repeat checks solely because the coordinator is handing off. Rerun affected checks and obtain renewed review when changes invalidate that evidence. Failed or unperformed mandatory checks prevent verified approval and the verified issue comment. For UI work, add relevant browser evidence when practical; missing authentication, unavailable tools, or an unperformed walkthrough is a verification gap, not a pass. Follow the active client's browser rules and the project's synthetic-data/authorization constraints.

Report delivered and partial criteria, changed files, review findings, exact commands/execution context, results/exit status, checked revision and scope, skipped/unavailable checks and reasons (including no configured tool versus configured but not run), browser evidence if obtained, remaining risks, model/delegation facts when observable, the issue comment URL, and closure readiness. Use `Fixes #N` or `Closes #N` only for complete delivery; otherwise use `Refs #N`. Keep parent issues open while required child outcomes remain incomplete. Tracker mutations other than the scoped verified issue comment, commits, pushes, merges, deployments, unrelated remote data changes, and messages follow existing user authorization and project rules.
