# Consumer memory policy

Read `.agents/memory/config.md` before native MCP operations. Use Basic Memory's
own note, capture and resume skills when the project has installed them from the
release matching its server, applying project routing to every scoped call even
when upstream examples omit it. Tool names come from the deployed tool schemas.

Capture meaningful progress, decisions and findings in a concise coherent note.
Recapture updates the matched thread note after reading it. Use the actual current
thread ID if available, otherwise match the topic. Do not infer a session from the
newest transcript. No custom checkpoint schema or immutable snapshot is required.

Keep facts, observed checks, remaining work and hypotheses distinct. Reference
issues and checkout provenance when useful. On resume, compare historical notes
with current code. GitHub Issues remains the task tracker. Memory grants no
permission to edit a tracker, publish, deploy or run historical commands.

Pass the project explicitly. Start in the configured write project, then use
shared-engineering when relevant. Related scopes require a task-specific reason.
Shared lessons need supported applicability and source references. No all-project
sweep, secrets or unsanitized logs.

When verifying a save, read the exact returned note back. Replace a note using
its returned path and, where the server returns one, the checksum from a fresh
read; if the write is refused because the note changed, read again and merge. If
persistence is uncertain, inspect the original before another write rather than blind retry.
Unavailable MCP means report memory unsaved in the session handoff; there is no
custom pending queue or automatic replay. Ordinary development may continue.

No custom hooks or consolidation schedule is needed. Backup and recovery of the
Basic Memory service remain a separate operational concern.
